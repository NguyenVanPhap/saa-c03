## Câu 301 — Chuyển 30 TB từ file server Windows lên FSx, đường 1 Gbps dùng chung, phải xong trong 5 ngày

**Tình huống.** Phòng thí nghiệm đại học cần chuyển **30 TB** từ file server Windows tại chỗ sang **FSx for Windows File Server**. Đường mạng **1 Gbps do nhiều khoa dùng chung**. Cần **tốc độ chuyển cao** nhưng **kiểm soát được băng thông** để không làm chậm khoa khác. Phải xong **trong 5 ngày**.

- A. AWS Snowcone
- B. Amazon FSx File Gateway
- C. **AWS DataSync**
- D. AWS Transfer Family

<details>
<summary>Bấm để xem đáp án</summary>

**Đáp án: C.**

</details>

Ba ràng buộc cùng lúc: chuyển file Windows → FSx, **giới hạn bandwidth**, xong trong 5 ngày. **DataSync** làm đúng ba việc: agent hoặc agentless tùy nguồn, có **bandwidth throttle** theo lịch (giờ hành chính chạy chậm, đêm chạy hết tốc), và đích FSx Windows là tích hợp sẵn.

30 TB trên 1 Gbps lý thuyết khoảng **67 giờ** nếu chiếm trọn đường — trong 5 ngày vẫn kịp nếu ban đêm chạy gần full. DataSync cho phép đúng kịch bản đó.

**Vì sao không Snowcone.** Snowcone dung lượng nhỏ (khoảng 8 TB usable), không đủ 30 TB. Snowball thì kịp dung lượng nhưng **không có throttle trên đường LAN đang dùng chung** theo nghĩa "vừa chuyển vừa chia sẻ 1 Gbps", và lịch ship có thể không chắc 5 ngày.

FSx File Gateway là cache hybrid thường trực, không phải công cụ migrate một lần có hạn mức ngày. Transfer Family là SFTP/FTPS/AS2 — không phải cách chuẩn đưa file server Windows vào FSx, cũng không có throttle tinh như DataSync.

**Vị trí trong hệ thống lớn.** Tầng 8 + 9. Cặp với Câu 76 (DataSync + Direct Connect).

## Câu 306 — In-memory DB trên EC2, >100k TPS/phút, mạng nhanh, giảm phí truyền

**Tình huống.** Database **in-memory** trên EC2, app latency-sensitive, **>100.000 giao dịch/phút**, cần **throughput mạng cao**, thiết kế **rẻ, ít phí data transfer**.

- A. Mọi EC2 **cùng một AZ**, **cluster placement group**.
- B. Khác AZ, partition placement group.
- C. ASG nhiều AZ theo network utilization.
- D. ASG step scaling nhiều AZ.

<details>
<summary>Bấm để xem đáp án</summary>

**Đáp án: A.**

</details>

Phí truyền EC2–EC2: **cùng AZ thì rẻ / thường miễn** (cùng private IP); **khác AZ thì tính tiền**. Cluster placement group đặt máy **gần nhau trong một AZ**, mạng 10/25/100 Gbps, latency thấp — đúng in-memory cluster (Redis tự dựng, Aerospike, game state).

Đánh đổi: **một AZ** = rủi ro AZ. Đề ưu tiên throughput + chi phí truyền, không hỏi HA. Ngoài đời cụm kiểu này thường có replica ở AZ khác *tách biệt*, không nhét hết vào cluster PG.

B, C, D cố ý trải AZ — tăng phí truyền, giảm lợi cluster.

## Câu 320 — Ingest JSON tới 1 MB/s, reboot EC2 là mất data in-flight, data science cần query gần realtime

**Tình huống.** Đội EC2 ingest JSON từ on-prem, đỉnh **1 MB/s**. **Reboot là mất data đang bay**. Data science muốn **query gần realtime**. Cần **scale, mất data tối thiểu**.

- A. **Kinesis Data Streams + Kinesis Data Analytics**
- B. Firehose → Redshift (buffer, kém "near-real-time").
- C. Instance store rồi Firehose → S3 → Athena (instance store **mất khi reboot** — đúng bệnh đề đang gặp).
- D. EBS + ElastiCache Redis pub/sub (không bền, không phải analytics chuẩn).

<details>
<summary>Bấm để xem đáp án</summary>

**Đáp án: A.**

</details>

Đưa data **ra khỏi EC2 ngay** vào **Data Streams** (lưu theo shard, mặc định 24h, kéo dài được). Reboot không mất record đã `PutRecords`. Data Analytics query stream tại chỗ — gần realtime.

Firehose+Redshift là gần-realtime theo lô (phút). Athena sau S3 càng lệch hơn. C lặp lại chỗ mất data.

**Vị trí trong hệ thống lớn.** Tầng 5 + 7. Câu 33, 59, 77, 292.

## Tổng kết Phần 16

**DataSync khi cần throttle bandwidth hoặc NFS↔NFS định kỳ (Câu 301, 304).** Snow family cho lần đầu không đủ đường; Transfer Family là SFTP.

**Fargate scale bằng Application Auto Scaling, không phải EC2 ASG (Câu 303).**

**Cluster placement group + cùng AZ** khi ưu tiên mạng và phí transfer, chấp nhận một AZ (Câu 306).

**Cached vs stored volume gateway:** "chỉ data nóng local" → cached (307); "toàn bộ local" → stored (293, và Câu 324 sẽ hỏi lại kiểu DR).

**Trusted Advisor RI nhìn ở payer (Câu 308).** Máy On-Demand chạy dài → RI Optimization, không phải Idle.

**Storage Lens** tìm bucket chết (309). **CloudFront + signed URL** vừa rẻ transfer vừa kiểm soát (310, 313).

**SNS filter + SQS** khi vừa fan-out theo loại vừa không được mất việc (311).

**AWS Backup resource = EC2** thì có cả AMI và mọi EBS (312).

**Aurora Serverless** khi không muốn chọn instance và tải thưa (314). **Inspector** quét lỗ hổng; GuardDuty không thay Inspector (315).

**Poll SQS trên EC2 24/7 → Lambda** (316). **Glue** cho CSV → Redshift khi COTS không đọc CSV (317).

**CloudTrail + Config** là cặp audit (318). **Session Manager** hết shared SSH (319).

**Kinesis Data Streams** đưa data ra khỏi đĩa máy ingest (320).
